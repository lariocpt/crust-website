**Goal:** let an AI agent run your test stack without a shell. `crust mcp` is a
[Model Context Protocol](https://modelcontextprotocol.io) server over stdio —
JSON-RPC 2.0, one message per line. The agent's host spawns it once and calls
`tools/list`, which returns the advertised wrappers: run a
line, lint a line, run suites, boot a mock server, supervise dev processes,
mine logs. No meta-tool wrapping a CLI in the way; the agent sees
`crust_load_run` and calls it.

## Install & register

<InstallBlock />

Then register the server using your particular host's configuration schema.
For hosts using `mcpServers` (for example Claude-style configuration):

```json
{ "mcpServers": { "crust": { "command": "crust", "args": ["mcp"] } } }
```

VS Code uses a different schema (`.vscode/mcp.json` per workspace, or the
user-level MCP settings) — the `mcpServers` shape above silently fails there
("command is required", or the server just never appears):

```json
{
  "servers": {
    "crust": { "type": "stdio", "command": "/ABS/PATH/to/crust", "args": ["mcp"] }
  }
}
```

Prefer an **absolute executable path** when a GUI host's `PATH` differs from
your shell; bare `"crust"` works only if the host can resolve it, otherwise
it fails with an error such as `spawn crust ENOENT`. Code - OSS/VSCodium needs
an MCP-capable host extension. Each host/extension has separate settings and
tool-exposure policies: availability in Copilot does not register the server
with another agent.

New grammar is available through `crust_run_line` when the installed binary
supports it. Dedicated tools still have wrapper schemas; new CLI arguments
do not automatically become new MCP arguments or tools.

`crust mcp` is a whole-process **mode**, not a REPL builtin: it takes over
stdin and stdout for the connection, which only makes sense as a process the
MCP host owns. A `mcp` line typed at a crust session refuses with that reason
instead of sh's misleading `command not found`. `crust mcp --help` prints the
same contract from the terminal.

## Verify by hand

The transport is just lines on stdin, so `printf | crust mcp` is a real smoke
test — initialize, then ask for the tool list:

```bash
printf '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"smoke","version":"0"}}}\n{"jsonrpc":"2.0","method":"notifications/initialized"}\n{"jsonrpc":"2.0","id":2,"method":"tools/list"}\n' | crust mcp
```

One JSON-RPC frame per line back. `initialize` echoes a protocol version from
the set this server speaks (`2025-06-18`, `2025-03-26`, `2024-11-05`); a
version it does not implement is answered with the newest one rather than a
promise the server cannot keep.

## Two execution planes

What persists between tool calls is the whole design question, and the tool
names answer it.

**One-shot tools** run a fresh crust child per call and return its captured
streams. Real exit codes, killable process groups, and schema-supported
overrides apply **per call, never as a persistent session**:

| Tool | The capability it exposes |
|---|---|
| `crust_run_line` | any crust line — the full grammar: pipelines, verbs, `sql`, `procs()`, asserts |
| `crust_check_line` | `--check` as a linter: parses without running, so generated crust is validated before it costs a run |
| `crust_test_fixture` | `.crust.ts` fixtures — matchers, JUnit/JSON reports, `-j`/`-n` stress runs |
| `crust_test_pipes` | `.pipes` suites with `-s` setup context |
| `crust_gen_fixtures` | OpenAPI spec → supported negative cases + qualifying CRUD flows, plus `gen-manifest.json` provenance and omissions; effective security/query prerequisites can omit an operation or whole candidate flow |
| `crust_verify_web_links` | sitemap crawl: links, anchors, redirects, OG/meta, JSON output — failures name their source page and element kind (0.3.6) |
| `crust_load_run` | paced load: `load … \| parallel … \| … \| stats`, with optional post-stats `assert` predicates (one string or an array); no automatic request-success gate |

**Schema exceptions matter:** `crust_check_line` accepts only `line` and has
a fixed 15s watchdog. `crust_gen_fixtures` and `crust_verify_web_links` accept
`cwd`/`timeout_ms`, but not `env`. Run-line, test, and load tools accept `env`
overlays on the inherited environment. Generator `parameterValues`,
`resolveParameter`, and `expectations` are setup-module exports, not
top-level MCP arguments. Generation deletes and recreates `out`; review its
manifest before separate, approved execution.

**Lifecycle tools** run *in-process* and stay **held across calls** for as
long as the host keeps the server open — a mock started in one call is still
serving three calls later:

| Tool | Holds / does |
|---|---|
| `crust_mock_server_start` | boots an OpenAPI mock (example-first, `stateful`, `state:` persistence, `validate`, `proxy` conformance audits). `port: 0` default — OS-assigned, collision-free; **use the returned `url`** |
| `crust_mock_server_stop` / `_list` / `_violations` | teardown, inventory, and the proxy-mode findings: what a real API does that its own `openapi.json` forbids |
| `crust_procs_start` / `_stop` | supervises a dev stack — per-proc env, `after:` ordering, `ready:` probes, restart backoff, process-group kill |
| `crust_logs_open` / `_query` / `_close` | a held tail / shell command / `procs({…})` source behind a ring buffer; queries are ordinary pipeline fragments over the buffered past, then a bounded live window (`live_ms`). Procs sessions share the same query tool — items are `{proc, stream, line}` objects |

A typical sequence: `crust_procs_start` the dev stack → gate with
`crust_run_line` on `wait :3000/health` → `crust_load_run` with an `assert`
threshold → `crust_logs_query` the survivors → `crust_procs_stop`.

## Tool classes — side effects up front

The `initialize` handshake carries this taxonomy in `instructions` (0.3.6),
so an agent sees it before its first call:

| Class | Tools | What it touches |
| --- | --- | --- |
| **Static check** | `crust_check_line` | launches a syntax-check child, possibly `sh -n`; does not execute supplied stages, read their data files, send their requests, or inspect TypeScript fixture contents |
| **Execution** | `crust_run_line`, `crust_test_fixture`, `crust_test_pipes`, `crust_gen_fixtures` | arbitrary stages with real side effects — target approval, credentials, writes and cleanup remain the caller's responsibility |
| **Network / load generation** | `crust_verify_web_links`, `crust_load_run` | bounded generation against the network — approved non-production targets only |
| **Long-lived resources** | `crust_mock_server_*`, `crust_procs_*`, `crust_logs_*` | held by the server process; die when it exits |

**Teardown has three tiers; stopping local resources is not data cleanup:**

1. **Local processes** — `crust_procs_stop` (and server exit) kill the
   supervised process groups whole: SIGTERM→SIGKILL, grandchildren included.
2. **Mock-server sessions** — `crust_mock_server_stop` closes the listener and
   releases the port. `--state` files and databases are application data: they
   stay on disk.
3. **Application data** — teardown does not delete remote/backend resources
   or application data. Execution tools can create, change or delete that
   data; stopping their local processes does not undo it. A container a proc
   started, a row it wrote, or a queue it filled survives local teardown; releasing it is
   the caller's job (`crust.onExit` covers scripted cleanup).

## Honest failure, ported to MCP

The wrapper preserves the child's answer; it does not independently judge
whether all requests or desired checks succeeded:

- A nonzero child exit or killed timeout is an **`isError` result** carrying
  its captured output (subject to announced caps). Failed asserts propagate
  through the child exit. Timed HTTP failures are records; proxy conformance
  violations are findings to inspect with `crust_mock_server_violations`,
  not automatic tool failures. `isError: false` is not request-success proof.
- **Load assertions are optional.** Without `assert`, an empty or all-failed
  measurement can exit 0. Supply status-first predicates, then latency/rate
  gates. With an assertion, tagged empty summaries are refused. Window/final
  guards need `stats_every`; without it those keys are absent and the
  threshold short-circuits. Drops warn on stderr, not as an automatic failure
  or stats-summary field. A passing minimum-rate gate can still have drops.
- A zero-match log query answers **"zero items"** — zero is an answer, not
  silence or universal failure.
- **Output is capped** per stream (256 KB, tail-kept) and truncation is always
  announced, never silent.
- **Lifetime is the host's.** stdin EOF, SIGINT or SIGTERM tear down every
  held job — mock ports closed, `procs` groups SIGTERM→SIGKILL'd whole —
  before the process exits, and a teardown still unwinding past 10s says so
  rather than claiming children are gone.
- **Every crust-side answer is a frame.** One-shot tools spawn a fresh crust
  child per call; lifecycle tools live in the server process. A successful
  result, a known-tool argument/run failure (`isError`), or a protocol error
  all arrive as JSON-RPC frames. Unknown tools and malformed parameters can
  be JSON-RPC errors instead of tool results. A host-side "unavailable tool"
  message alone does not diagnose the failing layer: inspect registration,
  tool exposure, and server frames before attributing it to Crust.
- **One call runs at a time.** The interrupt bus is process-global; two live
  windows draining at once would fire each other's children, so the server
  serializes.

## Configuration notes

- **`cwd` matters for lifecycle tools.** A relative spec path or seed file
  resolves against the **server's** working directory — set the host's
  `cwd` to your project root, or pass absolute paths.
- **`init.ts` loads normally** — registered functions and config apply to
  fragments run by `crust_logs_query`. A chatty config is harmless: at
  startup `process.stdout` is redirected to stderr before the config loads,
  so the protocol stream stays pure. Config is executable user code: a
  syntax-only tool does not make server startup side-effect-free.
- **`--env-file`** is honored at startup if your host passes it in `args`.
