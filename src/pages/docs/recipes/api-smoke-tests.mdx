**Goal:** point a folder of JSON fixtures at an HTTP service and confirm every one comes back `2xx`. Pure pipeline — no test runner, no framework.

This recipe works at three altitudes. Pick by how much each test needs to know:

- **One shell line** — the whole test is self-contained: body, headers, one assertion.
- **A `.pipes` file** — a *suite* of shell lines, run in order, with SQL/`assert` lines checking what earlier lines did.
- **`.crust.ts` fixtures (the TypeScript API)** — a single test needs multi-step logic: reuse a value from the response, generated tokens, per-fixture setup/teardown.

## The one-liner

<CodeSwitcher>
  <Fragment slot="bash">
  ```bash
  # read yields each file's CONTENTS (a bare glob would POST the paths)
  read fixtures/*.json | POST :3000/users | expect 201
  ```
  </Fragment>
  <Fragment slot="ts">
  ```ts
  await readAll("fixtures/*.json")
    .pipe(POST("http://localhost:3000/users"))
    .pipe(expectStage(201))
    .collect();

  // On mismatch, expectStage rejects with ExpectError { item, index, matcher }.
  ```
  </Fragment>
</CodeSwitcher>

`read fixtures/*.json` is a pipeline with one item per matched file — the file's **whole contents**, which `POST :3000/users` sends as the request body, per item. `expect 201` drains the stream and fails the pipeline (exit 1) naming the mismatch count. Add auth with `-H` (URLs, `-H` values and JSON literals are `$VAR` env-expanded):

```bash
read fixtures/*.json | POST $BASE/api/users -H "authorization: Bearer $TOKEN" | expect 201
```

## A typical fixture folder

```text
fixtures/
├── users/
│   ├── happy-path.json
│   ├── min-fields.json
│   └── extreme-name.json
└── auth/
    ├── refresh.json
    └── revoke.json
```

Each `.json` is the body for one request. Use as many as you like — every file becomes one item in the pipeline.

## A suite of one-liners — `.pipes` files

When one line isn't enough but every *test* still is, put the lines in a `.pipes` file: **one shorthand fixture pipeline per line**, `#` comments, blank lines skipped. `test-pipes` runs them **sequentially, in order** — on purpose, so a `sql | assert` line can check what the previous request wrote:

```bash
# smoke.pipes — request, then prove the DB saw it
{"name": "Court", "floors": 3} | POST $BASE/api/buildings -H "authorization: Bearer $TOKEN" | expect 201
sql "SELECT count(*)::int AS c FROM buildings WHERE name = 'Court'" | assert (r => r.c === 1)

# JSON-literal bodies are env-expanded too
{"name": "Annex", "parent": "$BUILDING_ID"} | POST $BASE/api/buildings -H "authorization: Bearer $TOKEN" | expect 201

# reads work as fixtures as well
GET $BASE/api/buildings -H "authorization: Bearer $TOKEN" | (r => r.json()) | assert (b => b.items.length >= 2)
```

```bash
test-pipes --target smoke.pipes
test-pipes --target 'tests/**/*.pipes' --bail --timeout 5000
```

`--bail` stops at the first failing line; `--timeout <ms>` fails any line that runs longer. Exit codes: `0` all pass, `1` any fail, `2` no files / bad args.

Two behaviors that keep suites honest:

- `assert (x => expr)` fails on falsy — **and on an empty upstream**. A `SELECT` that matches zero rows streams zero items, so a per-item predicate would never run; `assert` turns that into a failure ("no items reached") instead of a silent pass.
- Env expansion covers URLs, `-H` values, JSON literals and `sql` args. Lambda and `assert` bodies are JS — use `process.env.TOKEN` there, not `$TOKEN`.

### The setup module

Before a file runs, its setup module is imported and its **default export awaited**: pass `--setup <module>`, or drop a sibling `<name>.setup.ts` next to the `.pipes` file. Setup seeds `process.env` — that's where `$BASE` and `$TOKEN` come from:

```ts
// smoke.setup.ts — sibling of smoke.pipes, picked up automatically
export default async () => {
  process.env.BASE = "http://localhost:3000";
  const res = await fetch("http://localhost:3000/api/login", {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ email: "smoke@test.dev", password: "pw-123456" }),
  });
  process.env.TOKEN = (await res.json()).token;
};
```

Each `.pipes` file runs in a fresh, hermetic context — builtin fns like `sql` are registered, but your `init.ts` and aliases are not. A `.pipes` file must behave the same on every machine.

## The TypeScript API — `.crust.ts` fixtures

Reach for `.crust.ts` fixtures when a single test stops being expressible as one line: a value from the response feeds a later step, tokens are generated per fixture, matchers assert on structure, or the fixture needs its own `setup`/`teardown`. Each file is a normal TypeScript module that default-exports a fixture (or array) with `input` and `output`. Fields can be values *or* zero-argument thunks (resolved + awaited at run time). In `output`, a function with at least one parameter is a predicate matcher over the actual value.

`setup()`'s return value flows through the whole fixture: `input`/`output`
may be functions of the context, unary `input` field functions receive it,
and every matcher gets it as a second argument. Matchers may be **async** —
the runner awaits them, so asserting the DB side effect of a request is one
`await` away (stick to Bun builtins like `Bun.SQL` inside fixtures; the
compiled runner doesn't resolve third-party npm packages).

<CodeSwitcher>
  <Fragment slot="bash">
  ```bash
  test-fixture --target 'fixtures/**/*.crust.ts'
  test-fixture --target fixtures/users.crust.ts --out report.md
  ```
  </Fragment>
  <Fragment slot="ts">
  ```ts
  // fixtures/users.crust.ts
  export default {
    name: "GET /users/42 returns Lario",
    input: {
      method: "GET",
      url: "http://localhost:3000/users/42",
      headers: async () => ({
        Authorization: `Bearer ${await Bun.jwt.sign({ sub: "42" }, "k")}`,
      }),
    },
    output: {
      status: 200,
      data: { id: 42, name: "Lario" },
      headers: {
        "content-type": (v: string) => v.startsWith("application/json"),
      },
    },
  };
  ```
  </Fragment>
</CodeSwitcher>

## Matchers

In the `output` object you can mix exact values and predicates freely:

```ts
output: {
  status: 200,                                     // exact
  status: (s: number) => s < 300,                  // predicate
  data: { id: 42 },                                // exact (deep)
  data: (d: any) => d.id === 42 && d.email,        // predicate
  headers: {
    "x-request-id": (v: string) => /[a-f0-9-]{36}/.test(v),
  },
}
```

Predicates can also be `async` — useful for cross-checking against a database or another service.

## Status matchers via `expectStage`

When you're writing the pipeline in TypeScript directly, prefer `expectStage`:

```ts
expectStage(200);                        // exact status
expectStage("2xx");                      // class — "2xx" | "3xx" | "4xx" | "5xx"
expectStage((res) => res.status < 300);  // custom predicate
```

> The TS-test ecosystem owns the name `expect`. Crust exports it as `expectStage` to avoid collisions when you `import { expect as expectStage }` in test files. From the shell line it's just `expect 201`.

## Cross-check the database after a request

Status codes are necessary but not sufficient. The endpoint can return `201` and still write the wrong row — or no row at all. Crust ships a `sql` builtin backed by Bun's SQL client (via `$DATABASE_URL`), so you can pipe a POST response straight into a `SELECT` and assert on the result with a normal predicate lambda.

The shape: `POST → JSON → id → query → row → predicate`. Each `|` is one transform.

<CodeSwitcher>
  <Fragment slot="bash">
  ```bash
  # Set DATABASE_URL once per session
  export DATABASE_URL=postgres://app:app@localhost:5432/app

  # Create the user, then verify the row landed with the right values.
  # `Bun.sql\`...\`` template tags safely parameterize ${id}.
  # `assert` fails the pipeline on falsy — AND if no row reaches it.
  {"name": "Lario", "email": "lario@example.com"} \
    | POST :3000/users \
    | (r => r.json()) \
    | (u => u.id) \
    | (id => (await Bun.sql`select name, email from users where id = ${id}`)[0]) \
    | assert (row => row?.email === 'lario@example.com' && row?.name === 'Lario')
  ```
  </Fragment>
  <Fragment slot="ts">
  ```ts
  // The TS-API form composes the same stages with .pipe()
  await Pipeline.of([{ name: "Lario", email: "lario@example.com" }])
    .pipe(POST("http://localhost:3000/users"))
    .pipe(expectStage(201))
    .pipe(async (r) => (await r.json()) as { id: number })
    .pipe(async (u) => {
      const [row] = await Bun.sql`
        select name, email from users where id = ${u.id}
      `;
      return row as { name: string; email: string } | undefined;
    })
    .pipe((row) => {
      if (row?.email !== "lario@example.com") {
        throw new Error(`DB mismatch: ${JSON.stringify(row)}`);
      }
      return row;
    })
    .collect();
  ```
  </Fragment>
</CodeSwitcher>

### Using the `sql` builtin directly

When the query is constant — no upstream interpolation needed — call `sql` as a stage. It uses Bun's `$DATABASE_URL` client and **streams one row per item** as a source. As a transform, the static args become `(query, ...params)`; the upstream item is *not* auto-bound, so reach for a lambda when you need to inject a value from the stream.

<CodeSwitcher>
  <Fragment slot="bash">
  ```bash
  # Source — every recent user becomes one item downstream
  sql "select id, email from users order by id desc limit 5" | (r => r.email)

  # Transform with static params — last item passes through, params are constant
  range(0, 0)
    | sql "select count(*) as n from users where email like $1" "%@example.com"
    | (rows => rows[0].n)
  ```
  </Fragment>
  <Fragment slot="ts">
  ```ts
  // Source equivalent
  const emails = await Pipeline.of([])
    .pipe(() => Bun.sql`select id, email from users order by id desc limit 5`)
    .collect();

  // Or use Bun.sql directly when you're already in TS:
  const rows: Array<{ id: number; email: string }> = await Bun.sql`
    select id, email from users order by id desc limit 5
  `;
  ```
  </Fragment>
</CodeSwitcher>

### A `.crust.ts` fixture that does the same cross-check

If you'd rather keep the assertion declarative, do the DB check inside the fixture's `output` predicate. Predicate functions can be `async`, so `Bun.sql` works natively.

```ts
// fixtures/create-user.crust.ts
export default {
  name: "POST /users persists the row",
  input: {
    method: "POST",
    url: "http://localhost:3000/users",
    body: { name: "Lario", email: "lario@example.com" },
  },
  output: {
    status: 201,
    data: async (d: { id: number }) => {
      const [row] = await Bun.sql`
        select name, email from users where id = ${d.id}
      `;
      return (
        row?.name === "Lario" && row?.email === "lario@example.com"
      );
    },
  },
};
```

> Want to point at a different engine — Postgres vs. MySQL vs. SQLite vs. a read replica? See [DB drivers](/docs/db-drivers/).

## Reports & exit codes

```bash
test-fixture --target 'fixtures/**/*.crust.ts' --threads 8 --out report.json
```

Report format is picked from `--out`'s extension: `.json`, `.md`, anything else is plain text. With no `--out`, you get a colored folder-grouped summary on stdout.

Exit codes:

- `0` — all pass
- `1` — any failure / error
- `2` — no files matched, or bad args
