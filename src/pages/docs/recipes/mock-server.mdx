**Goal:** stand up a working HTTP mock from a Swagger / OpenAPI 3.x spec — useful for frontend dev before the backend exists, demoing a pipeline, or seeding fixture tests against an upstream you don't want to spin up.

## Boot a mock

<CodeSwitcher>
  <Fragment slot="bash">
  ```bash
  # Local spec
  mock-server --swagger ./openapi.yaml --port 4000

  # Remote spec
  mock-server --swagger https://petstore3.swagger.io/api/v3/openapi.json --port 4747

  # OS-assigned port, bind to localhost only
  mock-server --swagger ./spec.json --port 0 --host 127.0.0.1

  # Stateful mode — what you POST is what you GET back
  mock-server --swagger ./openapi.yaml --port 4000 --stateful
  ```
  </Fragment>
  <Fragment slot="ts">
  ```ts
  // Embed in a test harness — start + stop programmatically
  import { startMockServer } from "crust/mockServer";

  const handle = await startMockServer({
    swagger: "./openapi.yaml",
    port: 4000,
    host: "0.0.0.0",
  });

  // ... your tests ...

  await handle.stop();
  ```
  </Fragment>
</CodeSwitcher>

## Flags

| Flag | Default | Notes |
|---|---|---|
| `--swagger <url-or-path>` | *required* | URL or local `.json` / `.yaml` / `.yml`. Swagger 2.0 specs are auto-converted to OpenAPI 3.x. |
| `--port N` | `3000` | `0` requests an ephemeral OS-assigned port. |
| `--host addr` | `0.0.0.0` | Bind address. |
| `--stateful` | off | In-memory CRUD layer on top of example mode — see below. |

## How responses are picked

The server walks the operation in this order to choose a body:

1. `content.<media>.example` wins outright.
2. Otherwise the first entry in `content.<media>.examples`.
3. Otherwise the schema is walked:
   - `string` → `"string"` (or a format-aware default for `email`, `date-time`, `uuid`, `uri`).
   - `integer` / `number` → `0`.
   - `boolean` → `false`.
   - `array` → `[item]`.
   - `object` → every property generated.
   - `enum` → first value.
   - `allOf` → merged.
   - `oneOf` / `anyOf` → first branch.
4. Local `$ref`s into `components.schemas.*` are resolved (cyclic refs return `null`).

**Status code selection** within a matched operation:

```
200 → 201 → first 2xx → default → first defined
```

`application/json` content is preferred; otherwise the first content type wins.

**Routing**: literal segments take precedence over `{param}` siblings, so `GET /pets/mine` wins over `GET /pets/{id}`.

## What you'll see

Unmatched paths return `404`. Matched paths with the wrong method return `405`. Per request, one line goes to stderr:

```text
GET    /pets        200  3ms
POST   /pets        201  2ms
DELETE /pets/99     404  0ms
```

`Ctrl-C` (or `SIGTERM`) shuts the server down cleanly.

## Stateful mode — `--stateful`

Example mode replays the same spec example forever — fine for "does the client render a pet", useless for "create a pet, then edit it". `--stateful` adds an in-memory CRUD layer so the mock *remembers*:

- `POST` on a collection **creates** — the stored item is the spec-synthesized base merged **under** your request body, plus an `id` (yours if the body has one, else a random uuid).
- `GET` on an item returns exactly what's stored; `GET` on the collection returns everything stored, **shaped like the spec's collection envelope** (a documented `{ items: [...] }` wrapper is preserved; a bare array stays a bare array).
- `PATCH` / `PUT` **merge** the body over the stored item. `DELETE` removes it and returns `204`. Unknown ids are `404`.
- **Untouched collections keep serving spec examples** — consumers see no change until they write.

A full round trip:

```bash
mock-server --swagger ./openapi.yaml --port 4000 --stateful &

curl -s -X POST :4000/pets -H 'content-type: application/json' \
  -d '{"name": "Rex", "tag": "dog"}'
# → {"id":"1b2e…","name":"Rex","tag":"dog"}   (spec base + your body + id)

curl -s :4000/pets/1b2e…
# → the same item back — not the spec example

curl -s -X PATCH :4000/pets/1b2e… -H 'content-type: application/json' \
  -d '{"tag": "good dog"}'
# → {"id":"1b2e…","name":"Rex","tag":"good dog"}   (merged)

curl -s -X DELETE :4000/pets/1b2e…   # 204
curl -s :4000/pets/1b2e…             # 404 {"error":"not found"}
```

**When it beats example mode:** any client flow that reads its own writes — create-then-list screens, edit forms, optimistic-UI reconciliation, multi-step wizards, and fixture suites that assert on round-tripped values. Stick with plain example mode when you want deterministic, spec-exact bodies on every request. State lives in memory only; restarting the mock is a clean slate.

## Pairing with crust pipelines

The mock is just an HTTP server — drive it with normal crust pipelines.

<CodeSwitcher>
  <Fragment slot="bash">
  ```bash
  # Smoke-test every fixture against the mock
  mock-server --swagger ./openapi.yaml --port 4000 &
  test-fixture --target fixtures/*.crust.ts --out report.md

  # Burn-in: 10k requests across 100 workers
  range(0, 9999) | parallel 100 | GET :4000/pets | expect 200 | stats
  ```
  </Fragment>
  <Fragment slot="ts">
  ```ts
  // Start the mock, run a burn-in, tear it down
  import { startMockServer } from "crust/mockServer";

  const mock = await startMockServer({ swagger: "./openapi.yaml", port: 4000 });

  await range(0, 9999)
    .pipe(parallel(100, () => fetch("http://localhost:4000/pets")))
    .pipe(expectStage(200))
    .to(stats());

  await mock.stop();
  ```
  </Fragment>
</CodeSwitcher>

## Limits

Honest about what doesn't work yet:

- Remote `$ref` resolution
- Request validation (the mock accepts anything that routes — even in stateful mode)
- Faker-style data (every `string` is just `"string"` unless the format is known)
- Hot-reload on spec changes
