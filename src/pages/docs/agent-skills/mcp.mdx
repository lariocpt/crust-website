**`crust-mcp`** is the tenth embedded skill. It teaches an agent what it can't
guess from tool names alone: the two execution planes, what survives a call
boundary, and how to read a failure. The human-facing half — installing and
configuring `crust mcp` — is on [MCP server](/docs/mcp/); this page is what
the skill puts inside the agent.

## The plane question comes first

Every task starts with one fork: **run-and-return** or **hold-open**.

One-shot tools (`crust_run_line`, `crust_check_line`, `crust_test_fixture`,
`crust_test_pipes`, `crust_gen_fixtures`, `crust_verify_web_links`,
`crust_load_run`) spawn a fresh crust child per call. The skill's warning
here is the one an agent gets wrong by instinct: **there is no session**.
Supported `cwd` and `env` overrides apply to one call — `cd`-ing in one call
does not move the next. Check schemas: `crust_check_line` accepts only `line`
(fixed 15s watchdog); generation and link verification accept `cwd` and
`timeout_ms`, but not `env`. The run-line, test, and load tools accept `env`
overlays on the inherited environment:

```json
{ "name": "crust_run_line", "arguments": { "line": "cat config.json | json get port", "cwd": "/srv/app" } }
```

Lifecycle tools (`crust_mock_server_*`, `crust_procs_start/stop`,
`crust_logs_open/query/close`) are held by the server process across calls —
a mock boot in call three answers a request in call nine — and **every held
job dies when the server exits**, so the skill pushes agents to stop tools by
id and never to assume a session outlives the conversation.

## Side-effect classes and teardown tiers

Beyond the plane fork, the skill names four tool classes by what they touch —
**static check** (`crust_check_line`, syntax-only child, possibly `sh -n`), **execution** (arbitrary
stages, real side effects; target approval, credentials, writes and cleanup
stay the caller's job), **network/load generation** (bounded, approved
non-production targets only), and **long-lived resources** (held by the server
process). And three teardown tiers: local processes are killed whole, mock
sessions close (port released — `--state` files and databases are application
data and stay), and application data is not undone by teardown — execution
tools CAN mutate or delete it. A container or row a proc created remotely
survives its local teardown. The same taxonomy ships in
the `initialize` handshake's `instructions` (0.3.6), so an agent sees it
before its first call.

## Validate before you spend a run

`crust_check_line` is `--check` over the wire: it checks Crust command text
without executing those stages, reading their data files, or sending their
requests. It launches a child and may launch `sh -n`; it does not inspect
TypeScript fixture contents or prove runtime success. The standard loop is
check, then run only the approved scope. MCP startup loads normal user config,
so starting the server itself is not side-effect-free.

## Reading failures correctly

Nonzero child exits and killed timeouts yield `isError` with captured output;
failed asserts propagate through the exit code. `isError: false` is not
independent request-success proof: timed HTTP failures are records, and
proxy violations are findings to inspect explicitly. Known-tool argument/run
failures are tool errors; unknown tools and malformed protocol parameters
can be JSON-RPC errors instead. Two honest answers that are not failures:

- **"zero items"** — the query ran and matched nothing; zero is an answer.
- **announced caps** — 256 KB of output per stream, tail-kept, truncation
  always stated. An announced truncation is not a corrupted run.

**Load needs supplied gates.** `crust_load_run` adds no assertion when `assert`
is omitted; an empty or all-failed measurement can exit 0. Put status first,
then performance, for example `assert: ["s => s.status["200"] === s.count",
"s => s.p95 < 250"]`. With an assertion, tagged empty summaries are refused.
Window/final guards need `stats_every`; without it they short-circuit.
Drops warn on stderr, not as automatic failures or a stats-summary field.
Keep `expect` out of `target` when the summary must survive a status failure.

## Picking the lifecycle tool

- A dev stack goes to `crust_procs_start` — per-proc env, `after:` ordering,
  `ready:` probes — and its merged stream is queried with
  `crust_logs_query`, items being `{proc, stream, line}` objects. Readiness
  is gated in a follow-up `crust_run_line` with `wait :3000/health`, not by
  sleeping.
- A tail or container log goes to `crust_logs_open`; iterating on filters is
  then free — fragments run over the buffered past first, live only for the
  `live_ms` asked, `json: true` parsing NDJSON items before the fragment.
- A mock goes to `crust_mock_server_start` with the default `port: 0`
  (OS-assigned) and the **returned url** is used verbatim. `proxy: "<upstream>"`
  turns the mock into a conformance audit of a real API; findings come back
  from `crust_mock_server_violations`.

## Traps

- **Session state does not exist between one-shot calls.** No `cd`, no
  `export`, no aliases carried — pass only schema-supported overrides.
- **Host configuration is not shared.** Copilot registration does not
  register the server in another agent. Use that host's schema and tool
  exposure controls; prefer an absolute binary path when GUI PATH differs.
- **CLI grammar does not extend dedicated schemas automatically.** New
  syntax is available through `crust_run_line`; named wrappers still need
  explicit argument support. Generator prerequisite options belong in the
  setup module; `out` is deleted/recreated and omissions need review.
- **Relative paths in lifecycle tools resolve against the server's cwd**, not
  the agent's idea of "here". Absolute paths, or set the host's `cwd`.
- **One call runs at a time.** A long `crust_verify_web_links` crawl blocks
  the queue — raise `timeout_ms`, and don't call it "in parallel" with
  anything.
- **A procs `stop` past 10s can report "teardown still in flight"** — a child
  ignoring SIGTERM is being killed; it is not a successful stop pretending.
